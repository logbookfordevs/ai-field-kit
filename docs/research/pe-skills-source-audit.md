# PE Skills source audit

Audited 2026-09-16 for Leonardo's AFK comparison. Source: `backnotprop/product-engineering`, downloaded checkout `/tmp/afk-pe-research`, commit [`0642a58496d4dfa1de9688a82c29dfa34d24370a`](https://github.com/backnotprop/product-engineering/tree/0642a58496d4dfa1de9688a82c29dfa34d24370a).

This is an audit of PE, not an AFK comparison. All seven root `SKILL.md` files were read, alongside relevant mode references, report schema/validator/renderer/test source, the product-description link checker, derivation receipts, provenance manifest, ruling ledger, upstream watcher, integrity CI, and maintenance runbooks. External instructions were treated as source material. No skills were installed, no prescribed workflow was followed, no upstream automation was executed, and no product behavior or live GitHub CI outcome was verified.

## Assessment

PE is a thoughtful consolidation of frontend craft and workflow instructions, with six working skills and one router. Its distinctive assets are the combination of explicit ownership by deliverable, a vendoring maintenance system, an outside-in behavior-documentation workflow, and a concrete verification-report implementation. It is not an autonomous product-development runtime or a general engineering lifecycle covering backend architecture, deployment, and issue management. The shipped entrypoints route to UI design, UI implementation, UI judgment, behavior verification, behavior documentation, and brand assets. [Router](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/product-engineering/SKILL.md)

Selective adaptation is the stronger default for an existing skill ecosystem. Raw installation is reasonable for a user who wants PE's own working conventions and accepts its frontend preferences, stop points, `.product/` records, and inter-skill dependencies. The source provides useful intellectual material, but some untouched upstream procedures conflict with PE's new wrappers. Preservation and integration quality must be assessed separately.

## Every skill: value, boundaries, dependencies

### `product-engineering`

A front door that chooses by requested deliverable and then loads the owner completely. It distinguishes quality judgment from proof of behavior, existing behavior specs from plans for something new, reviewing animation from implementing it, and a diff/PR from a screen. It yields when a specific skill already matches. It adds discoverability and disambiguation, not another implementation capability. It depends on the six named siblings being available. [Source](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/product-engineering/SKILL.md)

### `pe-design`

Six modes: understand, brief, direct, mock, vary, onboard. Understand separates product truth (`PRODUCT.md`) from observed or selected visual truth (`DESIGN.md`); brief is scoped to a feature; direct derives a visual direction from the subject; mock supplies HTML fidelity levels; vary combines a real picker with one primary experimental axis and an accessibility floor; onboard is oriented around first value and interruption/recovery. Approval records preserve an approved artifact and its source under `.product/approved/<slug>/`, with state, decisions, exclusions, and supersession rather than deletion. This provides a concrete design-to-build-to-fidelity-review handoff. [Root](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-design/SKILL.md), [variation axes](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-design/references/vary/axes.md)

Costs and limits: brief explicitly confirms and stops without implementation; the approval path confirms a slug and asks when praise is ambiguous; variants stop for selection. Understand introduces a real external dependency: unversioned `npx @google/design.md spec/lint/export/diff`; it forbids showing a draft before lint/export pass. That gate can prevent even a provisional document from being delivered in offline or tool-restricted environments. The source itself provides no graceful fallback for that validation gate. Source-derived exact token claims are usefully constrained by observation, basis, and implementation consequence. [Brief gate](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-design/references/brief/index.md#L91), [validation dependency](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-design/references/understand/url-and-validation.md#L40)

### `pe-build`

Four modes: craft, motion, accessibility, harden. A shared boundary/evidence/triage/implement/verify/report loop protects an incumbent identity and prioritizes blocked tasks and missing recovery over polish. Approved artifacts constrain implementation; deviations must be stated. Verification is bounded to at most two visual rounds. The corpus includes accessible forms/focus/semantics, typography/layout/color detail, gesture physics and motion vocabulary, React View Transition recipes, resilience matrices, adaptation, performance diagnosis, and shipping metadata. [Root](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-build/SKILL.md), [build receipt](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/derivations/build.md)

This is substantial UI implementation guidance, not demonstrated code correctness. House choices are strong: press scale exactly 0.96, zero spring bounce except explicitly playful direction, ease-out exits, named curves, and never-disabled submit buttons. Its library list favors a specific React/frontend ecosystem; generation guardrails mandate Tailwind defaults, `motion/react`, and `cn`. The outer promise to follow the existing stack therefore needs precedence clarification when applied outside that ecosystem. The optional animations.dev material requires a purchased local pack; the public slot is only a README, and the pack is not distributed. [Library choices](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-build/references/craft/library-choices.md), [generation constraints](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-build/references/craft/generation-guardrails.md#L21), [course installer source](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/scripts/course-dropin.sh)

### `pe-review`

Nine modes are in the actual root table: change, screen, improve, guidelines, stress, motion, opportunities, accessibility, fidelity. This is broader than the older counts in some receipts and cards. The engine provides six ordered domain passes, evidence requirements, 13 automatic HIGH escalation triggers, a cheaper-fix ladder, root-cause consolidation, reported coverage, a 15-finding cap, and Block/Approve verdicts. Change review separates introduced/regressed problems from pre-existing findings; fidelity compares against the approved record. Improve supplies executable plans rather than edits. The screen workflow keeps experience judgment and mechanical inspection as separate passes. [Root](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/SKILL.md#L24), [engine](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/references/engine.md), [screen flow](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/references/screen-review.md)

It depends on `pe-build`'s domain references for much of its depth, so installing only review is not equivalent to installing a self-contained review corpus. Its preserved engine still tells the agent to ask the user to invoke `interface-review`, a name absent from the root's alias table, even though the root already handles change mode. Stress requires a scratch route and report annotations in the codebase, which needs an explicit harness exception to the wrapper's strict “never edits code” description. These are integration ambiguities, not evidence that a particular run failed. [Engine routing conflict](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/references/engine.md#L34), [stress harness](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/references/stress.md#L31)

### `pe-verify`

The most concrete new runtime component. It derives feature checks or reads a Markdown QA list, classifies checks as code/browser/mixed, and reports pass/fail/flag/skipped/not-run. Selective runs retain every excluded entry with a reason and selection basis. Browser capture uses Playwright recording plus checkpoint screenshots. A Python validator and renderer produce a branded HTML ledger/viewer, optional ffmpeg WebM-to-MP4 conversion, search/filtering, checkpoint player, and screenshot lightbox. `checked_by` can expose worker identity; orchestration permits agents or sequential execution. Reports default to system temp, with durable copies only on explicit request. [Root](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/SKILL.md), [renderer](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/scripts/render-report.py), [template](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/assets/report-template.html)

The validator checks allowed fields, IDs, statuses, selection rules, media path safety/existence, checkpoint order, and a single item in feature mode. It does not establish that the agent actually executed a check, reconcile report items with the source Markdown list, or require findings/evidence for a fail/flag. Indeed the test source deliberately accepts a failed report without findings. Thus “evidence or no finding” remains an instruction, not a fully enforced data invariant. There are 53 statically identifiable direct assertion calls plus one dynamic call inside the browser-results loop; these tests were read, not run in this audit. CI's integrity workflow does not invoke them. [Validator](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/scripts/validate_report_lib.py#L91), [sparse-failure test](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/scripts/test-render.py#L113), [integrity CI](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/.github/workflows/integrity.yml)

Portability is mixed. Python helpers have no third-party Python dependencies, ffmpeg is optional, and unavailable browsers cause skips rather than blocking code checks. Browser work specifically assumes Playwright and records a fixed 1280×800 viewport, one locale, reduced motion off, and one page per item; popup/second-page behavior is redirected to one page or skipped. That is a constrained evidence protocol, not comprehensive mobile, assistive-technology, or multiwindow coverage. QA discovery also creates a kit-specific home note at `~/.product-engineering/memories.md` after learning a custom list path. Temp storage improves cleanliness but weakens long-term evidence retention unless the user explicitly saves a run. [Capture protocol](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/references/evidence.md#L5), [QA and memory conventions](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-verify/references/qa-list.md#L5)

### `pe-product-description`

A demanding behavior-spec production method: inspect code/tests; fix vocabulary and interaction phases; write a pilot, foundations, and the hardest area sequentially; delegate independent documents; consolidate consistency; create manual verification checklists; deduplicate suspected defects into triage. Stable IDs, source commit footers, state diagrams, interrupts, foundation ownership, and explicit unknowns support continuation and auditability. Product-kind mappings cover canvas editors, web apps, CLIs, and chat products. A Python checker tests relative Markdown links and heading anchors. [Root](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-product-description/SKILL.md), [templates and checker](https://github.com/backnotprop/product-engineering/tree/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-product-description/references)

This is useful when a maintained, outside-in behavior corpus is the actual deliverable. It is heavy for a short feature spec: a new repository, scaffold/goal/glossary/agent instructions, numerous commits, 150–200-line pilot guidance, eight-section documents, and later verification/triage. Phase 3 explicitly requires subagents and supplies no sequential fallback. It withholds “verified” status based on automated passes alone, leaving a human verification dependency. On resumption it asks how to handle source-commit movement. The source repo remains read-only and filing upstream issues is separately authorized. [Workflow and gates](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-product-description/SKILL.md#L36)

### `pe-brand-assets`

SVG-in-code brand production, with a useful distinction between inline SVG and external file consumption: theming, accessible metadata, intrinsic sizing, font fallback or outlined logo text, and raster export where needed. Brand facts come first; the skill refuses to invent them. It combines five meaning-based logo methods, board/panel composition, restrained typography-first proposals, two–three distinct logo candidates, and a required reject-and-redo pass. Its narrower remit is an advantage for deterministic editable vector assets. [Root](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-brand-assets/SKILL.md), [identity method](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-brand-assets/references/identity-method.md)

It needs brand truth or user-supplied provisional values and calls into design for missing context and anti-generic checks. There is no image-generation tool integration: the derivation explicitly says imagegen was omitted. Raster rendering is prescribed without a bundled exporter. Its typographic/restraint default is an authored taste choice, not a neutral fit for every commissioned asset. [Derivation](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/derivations/brand-assets.md)

## Provenance, licensing, and watcher reality

The manifest has 131 entries: 100 `verbatim`, 7 `verbatim-minus`, 7 `distilled`, and 17 `authored`. Twenty are private course entries absent from the public checkout. Existing entries therefore comprise 80 verbatim, 7 patched, 7 distilled, and 17 authored. Ten upstream identities are recorded: nine remote sources and one private local course pack. An independent read-only SHA-256 comparison found all 94 present hash-bearing entries matched and no required manifest file was missing. This check did not fetch upstream blobs or replay patches. [Manifest](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/MANIFEST.json)

The public sources cover Emil Kowalski, Jakub Krehel, ibelick, Plannotator, Vercel's two repositories, Leon's taste-skill, Steve Ruiz's gist, and Impeccable. The repository's own work is Apache-2.0; manifest/NOTICE identify MIT upstreams and Impeccable's Apache provenance. Steve's gist has no license file: the repository asserts permission via Twitter but does not link a permission record. Redistribution/adaptation should preserve the relevant notices and verify permission scope rather than treating the repository-wide Apache label as applying to every file. The private course pack is explicitly excluded. This is a provenance observation, not a legal conclusion. [NOTICE](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/NOTICE), [LICENSE](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/LICENSE)

The integrity gate recomputes locked hashes and reconstructs patched files from pristine copies. It rejects unclassified reference files, with a course README exception. Authored entries skip hash validation; six authored root skills, report scripts/assets, and sample media are not manifest entries. Thus the README's byte-integrity statement is meaningful for vendored bytes, but the foundry overview's “every file” wording is broader than actual classification coverage. Hashes do not verify source quality, internal coherence, behavior, licensing permission, or correctness of authored glue. [Gate source](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/scripts/check-integrity.sh#L43), [foundry overview](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/README.md)

The scheduled watcher is detection and issue creation, not automatic updating:

1. Mondays at 14:00 UTC, or manual dispatch, fetch remote upstreams.
2. Compare each recorded source path at its pinned commit against the same path at current upstream HEAD. This detects tracked-file changes, including distilled sources; it does not discover valuable new files, assess improvement quality, or refresh private course content.
3. Report DRIFT/GONE; independently compare shipped `verbatim` bytes against their upstream pin for TAMPER.
4. Open a summary issue when such lines exist. No PR generation, dependency rewrite, or merge appears in the workflow. The re-lift runbook requires adjudication if a ruling conflicts and human approval to merge.

[Watcher workflow](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/.github/workflows/upstream-watch.yml), [comparison script](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/scripts/check-upstream.sh), [re-lift runbook](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/.claude/skills/foundry/runbooks/re-lift.md)

Operational gaps visible in source: issue creation is unconditional per drift-bearing run, with no search/update/deduplication of prior issues. The workflow deliberately disables immediate shell failure, captures a piped command's status, and only explicitly fails on status `2`; other comparison failures such as an upstream fetch error have no explicit fail step. It also relies on pipeline status propagation without declaring `pipefail` in that block. These merit hardening if adopting the watcher. Actual scheduled-run success was not inspected. [Workflow error handling](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/.github/workflows/upstream-watch.yml#L18)

## Composition method: valuable, but incomplete

PE grades inputs, classifies each file as verbatim/patched/distilled/authored, writes per-skill derivation receipts and explicit salvage/cut lists, then uses a single ledger for contradictions. Eleven rulings address press scale, bounce, reduced motion, exit easing, `will-change`, custom curves, stagger units, disabled submits, accessibility findings, motivated motion, and guideline house taste. The stated arbitration order is measured evidence, exact enforceable value, domain ownership, then an explicit logged decision. Some resolutions correctly discover a non-conflict, such as list-item stagger versus semantic-group stagger. [Ledger](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/LEDGER.md), [receipts](https://github.com/backnotprop/product-engineering/tree/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/derivations), [new-ruling runbook](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/.claude/skills/foundry/runbooks/new-ruling.md)

This makes editorial choices inspectable, but exactness is not correctness. Choosing 0.96 because it is easier to enforce is a consistency choice, not empirical proof that the surrounding range is worse. GOLD/SOLID/PADDED grades are the project's judgments, not an external benchmark. The ownership matrix is literally a preserved upstream `AGENTS.md`, including upstream installation/plugin instructions; it is maintenance evidence, not a clean PE-specific runtime contract. [Ownership matrix](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/ownership-matrix.md)

Concrete residual integration issues include:

- Original `interface-review` routing in the always-loaded review engine is not covered by PE's alias mapping.
- `stress.md` links `scenarios.md`, but the shipped file is `stress-scenarios.md`; the root tells the reader to load the correct file, yet the preserved link is not independently valid.
- Vary's preserved reference promotes the winner into production, while the PE root hands implementation to `pe-build`. It also links uppercase `PICKER.md` while the shipped path is lowercase `picker.md`, which matters on case-sensitive systems.
- The new-code guardrail has stronger stack mandates than the surrounding stack-portability promise.
- The product-description receipt still says whole/verbatim/no cuts; the actual manifest class is `verbatim-minus`, with a recorded patch for the `pe-` rename. This is stale explanatory text rather than missing provenance.

[Review engine](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/references/engine.md#L34), [stress link](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-review/references/stress.md#L27), [variant promotion](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/skills/pe-design/references/vary/index.md#L74), [product-description manifest](https://github.com/backnotprop/product-engineering/blob/0642a58496d4dfa1de9688a82c29dfa34d24370a/foundry/MANIFEST.json#L1171)

The practical lesson is to preserve the upstream baseline and maintenance record while normalizing runtime names, paths, precedence, and workflow gates. Byte preservation alone leaves the model responsible for resolving remnants of the original packaging.

Standalone-install distinction: the roots' `metadata.provenance` explicitly points to the foundry receipt “in the source repository”; those receipts are attribution metadata rather than required runtime reads. Foundry is maintenance tooling and is not necessary to execute ordinary skill modes. Within-skill references, report assets, and Python helpers are present in the downloaded skill directories. That does not make every skill independently complete: review explicitly reaches into build; brand reaches into design; the router needs siblings; and preserved aliases/relative links still need normalization. This audit verified source-directory availability, not the behavior of the external `npx skills` installer or its installed file selection.

## Recommendation input for AFK's separate comparison

| Candidate | Recommended treatment | Reason |
| --- | --- | --- |
| Verification JSON/report renderer | Strong selective-adaptation candidate | Concrete reusable output contract and implementation; strengthen evidence/status invariants, browser adapter, retention policy, and list reconciliation |
| Product-description method | Offer as an explicit specialist workflow | Strong state/interrupt/glossary/triage method, but expensive and procedural; keep a lighter feature-spec path separate |
| Provenance manifest + pristine patches + ledger | Reuse for genuinely vendored reference sets | Makes provenance and editorial changes auditable; avoid extending hash ceremony to ordinary authored prose without need |
| Approved artifact + exact approved state + supersession | Reconcile with existing artifact conventions | Useful fidelity contract; avoid adding parallel approval storage where an equivalent record already exists |
| Review evidence/coverage/consolidation and domain ownership | Compare and selectively retain missing rules | Valuable judgment discipline; fix source-routing remnants and explicit scratch-harness boundaries |
| Build/design domain references | Curate by actual gaps | Large overlapping frontend corpus and strong taste/stack assumptions; loading all of it is unnecessary |
| Router and brand SVG workflow | Optional user-facing conveniences | Good deliverable routing and vector-specific details; neither requires importing the whole workflow system |

Before raw installation or redistribution, resolve four open questions: which entrypoints genuinely add capability to the existing catalog; which PE gates and storage conventions the user wants; whether partial installation includes required sibling references; and whether the gist's permission scope covers the intended distribution. No raw install was performed or recommended as an automatic next step by this audit.
